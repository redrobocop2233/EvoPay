## 1. Project Identity

**Project:** EVO-PAY  
**Theme:** Adaptive Red-Team / Blue-Team payment fraud defense  
**Challenge:** Mastercard Innovation Challenge 2026 / Global Fintech Fest 2026

### Core challenge statement

Build an end-to-end Red Teaming AI system that:

1. **Identifies** novel emerging GenAI-powered payment fraud attacks.
2. **Generates** realistic simulations of those attacks at scale.
3. **Defends** against them with an accurate detection model.

The intended differentiator is a **closed feedback loop**:

```text
Identify → Generate → Attack → Detect → Autopsy → Mutate → Attack again
```

The attacks generated by the Red Team become the training and stress-testing ground for the Blue Team. Weaknesses found by the Blue Team feed back into the Red Team so future generations become harder to detect.

# 5. Three Pillars

## 5.1 IDENTIFY

GenAI is used as a threat-discovery / threat-intelligence layer.

The model receives context such as:

- Known fraud families
- Previously discovered attacks
- Weak behavioral dimensions
- Desired number of hypotheses

It returns structured attack hypotheses.

The system separates:

```text
transaction_simulatable
```

from:

```text
research_only
```

This is important because some GenAI-powered fraud concepts are useful for research but cannot or should not be reproduced directly in the transaction simulator.

# 7. ATTACK GENOME

The Red Team represents an attack as a vector of behavioral dimensions.

Current dimensions:

```text
amount
temporal
device
geographic
merchant
velocity
coordination
```

Each dimension is normally represented as a value between:

```text
0.0 → 1.0
```

Example:

```text
amount       = 0.77
temporal     = 0.00
device       = 0.00
geographic   = 0.93
merchant     = 0.40
velocity     = 0.80
coordination = 0.20
```

The genome is converted into behavioral primitives.

Examples:

```text
amount >= threshold
    → amount_spike

temporal >= threshold
    → odd_hour

device >= threshold
    → device_switch

geographic >= threshold
    → geo_anomaly

merchant >= threshold
    → category_drift

velocity >= threshold
    → velocity_burst

coordination >= threshold
    → multi_account_coordination
```

# 10. ATTACK CAMPAIGNS

The Red Team should generate **campaigns**, not merely isolated fraudulent rows.

A campaign contains:

```text
campaign_id
customer_id
genome_id
primitives
number of transactions
gain

```

A campaign can contain a sequence of transactions that express a behavioral strategy.

This is important because sophisticated fraud is often a **trajectory**, not a single anomalous transaction.

# 11. CURRENT RED TEAM BEHAVIORAL PRIMITIVES

The original Red Team implementation included:

```text
device_switch
odd_hour
amount_spike
geo_anomaly
velocity_burst
category_drift
```

The enhanced architecture adds:

```text
multi_account_coordination
```

The intended direction is to combine primitives rather than test each signal independently.

Example:

```text
geographic drift
+
merchant category drift
+
velocity burst
```

is more useful than generating only:

```text
large amount
```

because the goal is to explore combinations that can create detector blind spots.

# 12. EVOLUTIONARY RED TEAM

The Red Team uses evolutionary search.

Basic process:

```text
Initial population
       ↓
Generate campaigns
       ↓
Score campaigns
       ↓
Select strongest candidates
       ↓
Mutate genomes
       ↓
Generate next population
       ↓
Repeat
```

Mutation changes one or more genome dimensions.

Diversity is also measured to avoid the population collapsing too quickly around one strategy.

---

# 13. FITNESS

The standalone Red Team currently uses a detector-independent proxy:

```text
fitness =
    0.45 × realism
  + 0.25 × novelty
  + 0.30 × (1 - detectability_proxy)
```

This is a temporary standalone objective.

Once connected to the Blue Team, the preferred objective is detector-aware.

Conceptually:

```text
attack_success = 1 - detection_probability

fitness =
    0.50 × attack_success
  + 0.25 × novelty
  + 0.25 × realism
```

The exact weights can be tuned experimentally.

### Important design principle

The Red Team should NOT simply optimize for:

```text
largest amount
```

That produces unrealistic and easily detected attacks.

The goal is:

```text
realistic
+
novel
+
hard to detect
```

```text
+

+

```

and produces structured analysis such as:


The intended loop is:

```text
Attack
 ↓
Blue detects
 ↓
Autopsy asks WHY
 ↓
Identify weakest / most informative signal
 ↓
Recommend mutation
 ↓
Red mutates
 ↓
Attack again
```

This is one of the key differentiators of EVO-PAY.

```text
         1 |     90.9% |           9.1% |      0.2907 |   0.6940 |        8 |   0.9816
```


### Interpretation

The important result is not simply that the detector has high F1.

Across generations:

```text

```

This indicates that the Red Team is finding harder attack strategies.

The decreasing diversity score also indicates that the evolutionary population is converging. That is useful, but it is also a warning: future versions should explicitly preserve diversity to avoid premature convergence.

# 23. KNOWN / IMPORTANT ENGINEERING ISSUES

## Gemini availability

Gemini API calls can occasionally return:

```text
503 UNAVAILABLE
504 DEADLINE_EXCEEDED
RemoteProtocolError
```

The client has been made transport-resilient with retries/fallback behavior.

Do not interpret temporary provider errors as application logic failures.

## Automatic Function Calling warning

The Gemini SDK may emit a warning related to Automatic Function Calling when using `generate_content`.

The architecture does not require AFC for the threat-discovery task.

If the warning is still present, explicitly disable AFC in the request configuration where appropriate.

## Model naming

The project has used Gemini model names during development that may change over time.

Keep the model configurable through:

```env
GEMINI_MODEL=
```

Do not hard-code the model name throughout the project.

# 24. WHAT NOT TO DO

Do not:

- Add unnecessary ML models just to increase complexity.
- Make Gemini generate every transaction.
- Optimize Red Team only for transaction amount.
- Evaluate only on the same attacks used for training.
- Claim real-world fraud performance from synthetic data alone.
- Commit API keys.
- Couple Red Team internals tightly to Blue Team internals.
- Allow evolutionary diversity to collapse without measuring it.
- Treat a high F1 score on synthetic data as proof of production readiness.

# 26. CORE PROJECT THESIS

EVO-PAY is not just:

```text
"an AI fraud detector"
```

It is:

```text
"an adversarial synthetic environment that continuously
creates new payment attack trajectories and uses the
resulting failures to harden the detector."
```

The strongest demonstration is therefore not:

> "Our model has 95% F1."

It is:

> "The Red Team generated attacks, the Blue Team exposed which behaviors it could detect, GenAI diagnosed the remaining weakness, the Red Team mutated the attack, and the next generation became harder to detect."

That closed-loop behavior is the central concept of EVO-PAY.
